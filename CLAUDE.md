# CLAUDE.md

Guide for Claude Code sessions in this repository, local or cloud. It says how the framework is built, what to read
first, how a scenario flows through the layers and which checks guard the structure. The details live in the linked
docs; read them instead of guessing.

The project: one set of Gherkin features against the Toolshop demo shop, run by two suites, Playwright + TypeScript
(playwright-bdd) and Playwright for Java (Cucumber-JVM), with CI that boots its own pinned Toolshop, a nightly across
three browsers, and reports and a results page on GitHub Pages.

## Structure

```
features/                 shared Gherkin: api/ (A), ui/ (U), journeys/ (S), control/ (C1, C2: fail on purpose)
src/  (TypeScript)        java/src/test/java/com/showcase/  (Java, same layers)
  steps/       ↔ steps/            one sentence → one page method or API call, or an assertion on a module
  fixtures/    ↔ steps/Hooks, PlaywrightContext, ScenarioContext   injection, failure evidence, not-run steps
  pages/       ↔ pages/            what a user does on a page: actions and waits
  data/        ↔ data/             fresh test data, built through the API
  modules/     ↔ modules/          locators only
  api/         ↔ api/              API client per resource, response contracts (zod / Contracts)
  config/      ↔ config/           URLs and accounts (.env)
  tags.ts, reporters/, a11y/, visual/
tests/        quality/ (N1 visual, N2 a11y), architecture/ (N3), auth.setup.ts, ui/seed.spec.ts
              features/ is generated by `npx bddgen` (git-ignored, never edit)
scripts/      suite runner, demo, format, step catalogue, CI summary, Java report, Pages site, PR impact analysis
.github/      workflows/ (pr-smoke, pr-impact, nightly-regression, update-visual-baselines), actions/ (shared)
```

**Dependencies point down the layers only:** steps → fixtures → pages → data → modules / api → config. A module never
uses a page, a page never uses a step, the API layer never uses test data. Both languages follow the same rule.

## How a scenario flows

1. **ID:** a row in [docs/test-plan.md §3](docs/test-plan.md#3-test-inventory) with the next free number of its
   prefix; tier tag `@smoke` (PR gate) or `@regression` (nightly).
2. **Feature:** in `features/api|ui|journeys/`, title starts with the ID (`Scenario: U7: …`). Tags only from
   [src/tags.ts](src/tags.ts) (one tier per test; kinds like `@negative`, `@e2e`, `@admin`, `@logged-out`).
3. **Steps:** reuse sentences from docs/steps.md; a new UI step names its page ("… on the product page"), one action
   per sentence, API steps say "API". Write it in **both** languages: `src/steps/<feature>.steps.ts` and
   `steps/<Feature>Steps.java` (shared steps in `common.steps.ts` / `CommonSteps.java`).
4. **Page and module:** actions and waits in the page method, locators in the module, no fixed sleeps.
5. **Generate and run:** `npx bddgen` turns features into Playwright tests (every npm test script does it first);
   Java runs the same feature files through `RunCucumberTest`.
6. **Before pushing:** `npm run format`, `npm run steps` (rewrites docs/steps.md); the pre-push hook checks both.
7. **PR:** the PR gate runs static checks and both smoke suites; two comments show the scenarios the change can affect
   and a structure check. After merge, the nightly runs everything in three browsers and Java.
8. **Numbers:** a new test changes counts in README ("At a glance", the badge line), docs/test-plan.md and the results
   page text; keep them true.

## Commands

```bash
npm install && npx playwright install && cp .env.example .env   # once; npm install also sets the pre-push hook
npm run test:pr             # the PR gate's TypeScript suite (API + Chromium)
npm run test:api            # API features only, no browser
npm run test:architecture   # N3 rules, no browser, no Toolshop
npm run check:tags          # tags, tiers and IDs of every test
npm run steps               # rewrite docs/steps.md   (check:steps = the check)
npm run format              # Prettier, import order, Java Spotless   (format:check = the check)
npm run lint && npm run typecheck
node scripts/pr-impact.mjs --base origin/master   # the PR's first comment, for the current branch
cd java && ./mvnw test -Dgroups=smoke              # Java smoke (JDK 21)
cd java && ./mvnw test -Dcucumber.execution.dry-run=true -DexcludedGroups=   # every feature step has a Java step
```

## Checks that guard the structure

- **Architecture tests** ([tests/architecture/](tests/architecture/), N3, `@smoke`, PR static stage):
  - pipeline: no workflow can trigger or re-run itself, no cycles between actions or `workflow_run`, every job has a
    timeout, shell loops are bounded, Playwright runs only after `bddgen`, browsers install only through the cached
    action;
  - code: no cycle in TypeScript imports or Java class references (whole repository, new files and folders included),
    npm scripts and Playwright projects acyclic;
  - Gherkin layers: modules only declare locators, steps create no locators, page/module file naming, no hand-written
    `*.spec.js`;
  - parity: every scenario (A, U, S, C) in both languages, the test plan's Java column true, equal retries.
- **Other static checks:** ESLint, Prettier, `typecheck`, `check:tags`, `check:steps`, Java Spotless and compile,
  the Java dry run.
- **PR impact comments** (`.github/workflows/pr-impact.yml`, [ADR 0014](docs/decisions/0014-pr-impact-comments.md)):
  1. the scenarios and steps a change can affect, per language, with the chain of code that leads there;
  2. the structure check: the static checks, dependency cycles and layer direction across the repository, and every
     dependency the PR adds. Read both on every PR.

## Principles not to break

- Every scenario runs in TypeScript **and** Java with the same tier ([ADR 0009](docs/decisions/0009-every-journey-in-both-languages.md)).
- A failing test stays a failure: no known-issue markers, no expected failures; a test that did not run counts as
  failed; a rerun never hides a failed attempt ([ADR 0013](docs/decisions/0013-failures-stay-failures.md),
  [ADR 0011](docs/decisions/0011-retries-and-flaky-tests.md)).
- Both reports look and behave the same: the TypeScript Playwright HTML report is the reference; failure evidence is
  the screenshot at the failed step plus the trace for browser tests, nothing for API tests.
- CI never uses the public demo; Toolshop is pinned in `.github/actions/toolshop-start` (commit and Angular CLI).
- Changes reach `master` only through a PR (ruleset requires the smoke checks).

## Working in a cloud session

- Node 22 and JDK 21. What needs neither Toolshop nor a browser: lint, format, typecheck, `check:tags`,
  `check:steps`, `test:architecture`, `test:api` against the public demo, `pr-impact.mjs`, Java compile and dry run.
- UI and journey tests need a Toolshop: the public demo (`.env` default; `@admin` and `@own-toolshop` are skipped
  there, and its sign-in is sometimes unavailable) or the pinned Docker setup that CI starts
  (`.github/actions/toolshop-start` and `toolshop-ready`). Without either, push a branch and let the PR gate run them.
- Use `gh` for the rest: `gh pr checks <n>`, `gh run view <id> --log`, `gh run download <id> -n <artifact>`; the
  latest nightly's reports are on https://junchunip-hue.github.io/playwright-e2e-showcase/ (cached up to 10 minutes).

## Working with the maintainer

- Reply in Korean; everything in the repository (code, comments, commits, PRs, docs) stays in English.
- Commit, push, open or merge a PR, delete a branch or run the nightly only when asked. Usual requests:
  "고치기" → a branch and a PR; "병합 후 nightly" → merge (delete the branch), run `nightly-regression.yml` on master
  and report; "CI 끝나면 결과 알려줘" → wait and report the checks and what the PR comments say; "#N 성공하면 merge까지"
  → merge as soon as every check passes, otherwise report why not. If a PR number is unclear, ask.
- Prove claims with real runs: CI artifacts, the live reports and results page, not only a local run. After a merge,
  expect "README랑 첫 페이지 다시 확인해줘": compare them with the actual numbers and wording.
- Never put a token or password in chat or the repository.
